    Under the hood
    1. The page asks the API for a ZIP of generated statements and uploads it. 19 in 20 go with a token from the demo identity provider, the rest through the anonymous sandbox.
    2. The API checks the token (EdDSA, against the provider's published keys), looks inside the ZIP (size, file names, compression) and stores it in PostgreSQL together with an outbox row, in one transaction.
    3. The relay publishes each outbox row to NATS JetStream. Several relays can run; they skip rows another relay is working on.
    4. The importers (several, side by side) take a batch from the stream, check every file against the CAMT schema and the business rules, and book each statement in its own transaction. In strict mode the ZIP is one transaction with a savepoint per statement.
    5. Deadlocks happen because the importers update the same few accounts. The database ends one transaction; the core's retry runs it again. Nothing is lost.
    6. This page follows along through a Mercure hub in the web server. Prometheus scrapes every service every two seconds.

    Tokens and keys

    Send a small ZIP to the API and see who gets in. With a valid token the upload is accepted and recorded under the sender. Every broken token is refused for its own reason. The sandbox needs no token, but takes only small files.

    About

    Worker mode

    The application starts once and serves thousands of requests from memory. The container and the router are compiled when the image is built.

    Observable

    Every request has an id that follows it through the JSON log. Metrics are counted in shared memory, and the route is a label, never the raw URL.

    Secure

    Errors never leak internals, secrets come from files, the database enforces its own timeouts, and the container runs as a non-root user on a read-only file system.
